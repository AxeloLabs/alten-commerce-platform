== Principles

.Strategy question
****
What strategy gives confidence in every release without making every release wait for an hour of tests?
****

A test exists to answer one question, as cheaply as that question can be answered.
A business rule is proven by a test that runs in a millisecond; only what cannot be proven that way moves up to a slower level.

.Six principles
[cols="4,11", options="header"]
|===
| Principle | Meaning
| The lowest level that can prove it | A rule of the domain is tested in the domain. A test that starts a database to check an addition is a wasted second, a thousand times a day.
| Every identifier is tested | Each rule, scenario, saga path and error code of this specification is verified by at least one catalogued test (document 07-02). What is not traced is not known to be tested.
| Four families, always | A function is tested when it works, when it must refuse, at its limits, and for what must stay true whatever happens.
| Real where it matters | A database behavior is tested on the real database; a bus behavior on the real bus. Simulations are for neighbors, never for the thing under test.
| Deterministic | A test controls time, identifiers and order. A test that fails one time in twenty is a defect, treated as such.
| Written first | The acceptance scenarios exist before the code (document 01-08), and the state grids before the sagas (document 02-03): tests are derived from them, not from the implementation.
|===

== Levels

.Strategy question
****
What strategy decides how much of the system a test needs to start?
****

plantuml::diagrams/test-pyramid.puml[format=svg, align=center, pdfwidth=85%]

.The four levels and their identifiers
[cols="2,5,5,4", options="header"]
|===
| Level | What is under test | What is real, what is simulated | Tools
| Unit (`TU`) | One aggregate, value object, domain service or saga | Nothing is started. Time and identifiers are given by the test. No mock: the domain has no dependency to replace. | JUnit {v-junit}, AssertJ {v-assertj}
| Component (`TC`) | One service, through its interfaces: REST requests, messages in, messages out | Real: its database, the bus emulator, its own adapters. Simulated: the other services and the providers. | Spring Boot test support, Testcontainers {v-testcontainers}, Microcks {v-microcks}, WireMock {v-wiremock}
| Integration (`TI`) | One adapter against the technology it adapts; or several services together on one scenario | Real: PostgreSQL, Pub/Sub, Firestore, the services involved. Simulated: the providers. | Testcontainers; the `test` and `integration` environments
| End-to-end (`TE2E`) | A critical path, from the browser to the e-mail | Everything is real and deployed. The providers are the simulated ones of the platform. | Playwright {v-playwright}
|===

.How many, how fast, where
[%unbreakable, cols="2,3,3,7", options="header"]
|===
| Level | Order of magnitude | Each takes | Runs
| Unit | Many hundreds | Milliseconds | At every build, on a workstation and in the pipeline
| Component | About a hundred | Seconds | At every build
| Integration | Some dozens | Seconds to minutes | Adapters: at every build, in containers. Several services together: after deployment, in `test` and `integration`
| End-to-end | A handful per critical path | Minutes | After deployment to `integration`; a subset after every deployment, everywhere
|===

== Kinds of test

.Strategy question
****
What strategy covers every kind of test a project of this size needs, without inventing a tool for each?
****

The brief lists the kinds of test it expects.
Each is a purpose; most are served by one of the four levels above.

.Kinds of test, and how each is done
[cols="3,6,4,3", options="header"]
|===
| Kind | Purpose here | Done with | Level
| Unit | Every business rule; every cell of the state grids | JUnit | TU
| Component | A service keeps its contract, with its real adapters | Spring Boot tests, Testcontainers | TC
| Interface, on inputs and outputs | Every request and answer of a REST interface, every message in and out, conforms to its contract — errors included | Microcks against the OpenAPI and AsyncAPI documents; schema validation of messages | TC
| Integration | An adapter works with the real technology; services work together | Testcontainers; the deployed environments | TI
| Acceptance | The behavior agreed with the business holds | The Gherkin scenarios of document 01-08, run by Cucumber {v-cucumber} | TC or TE2E
| End-to-end | A critical path works for a customer | Playwright | TE2E
| Smoke | A deployment that just finished is alive: the critical paths answer | A subset of the end-to-end tests, tagged | TE2E
| Regression | What worked still works | Not a separate suite: every test above, run at every change. A defect found in production first becomes a test that fails. | All
| Architecture | The structure of the code is kept | ArchUnit {v-archunit} (document 04-03) | Build
| Mutation | The unit tests would notice a change of the domain | PIT {v-pitest} | Build
| Persistence contract | The three stores of the catalog and the cart behave alike | One suite, three adapters (document 04-04) | TI
| Saga and resilience | An order reaches an outcome whatever fails | The scenarios of document 07-03 | TI
| Security | Authorization holds; common attacks fail; nothing leaks | Document 07-04 | TC, TI, deployed
| Performance | The targets hold at the expected load and at twice that load | Gatling {v-gatling} (document 07-04) | Deployed
| Accessibility | The customer journeys meet the guidelines ({NFR-USAB-001}) | Automated checks inside the end-to-end tests | TE2E
| Migration | Every schema migration applies to an empty database and to the previous schema | Flyway {v-flyway} on PostgreSQL in a container | TI
|===

== Four families

.Strategy question
****
What strategy keeps tests from proving only that things work when everything goes well?
****

Every catalogued test belongs to one family.
A function is covered when it has tests of each family that applies to it.

.Families
[cols="2,6,7", options="header"]
|===
| Family | Question | Examples
| Nominal | Does it do what it is for? | An order is placed and confirmed; a product is published
| Error | Does it refuse what it must refuse, the right way? | A payment is declined; a retired product cannot be published; a customer asks for another's order
| Edge | Does it behave at its limits? | The tenth unit of a line and the eleventh; a price of 0.01; an answer that arrives at the same instant as a deadline; the last unit wanted by two customers
| Invariant | What stays true whatever happens? | Available quantity is never negative; an order is charged at most once; a rejected order holds no payment; a final status never changes
|===

Invariants are tested twice: by examples, like the others, and by tests that try many generated sequences of events against a saga or an aggregate and check the invariant after each step.
The state grids of document 02-03 make this possible: every event has a defined outcome in every state, so any sequence is a valid test.

== Acceptance scenarios

.Strategy question
****
What strategy keeps the sentences agreed with the business and the tests that run from drifting apart?
****

The acceptance scenarios of document 01-08 are written in Gherkin and are the only wording of expected behavior that the business reads.

.Rules
[cols="4,11", options="header"]
|===
| Subject | Rule
| One source | The feature files of the specification are the ones Cucumber runs. They are not copied: the build of the services reads them where they are.
| Automated once | Each scenario is bound to code at the lowest level that can prove it. A scenario about one service runs as a component test of that service. A scenario tagged as a critical path runs end to end as well.
| Steps | A step is bound to a call of the service's interface or of the storefront, never to its database. What a scenario cannot observe from outside, it does not assert.
| Identifiers | The tags of a scenario — its own identifier, its use case, its rules — are reported with its result, and feed the traceability matrix (document 00-03).
| A scenario with no binding | Fails the build. A sentence agreed with the business is never silently unverified.
| Changing a scenario | A change of the specification, reviewed as such, before the code changes.
|===

== Test doubles and test data

.Strategy question
****
What strategy keeps a test honest about what it really exercised?
****

.What may be replaced, and by what
[cols="4,5,6", options="header"]
|===
| Thing | In a test of | Replaced by
| The domain's dependencies | The domain | Nothing: it has none. Time and identifiers are parameters.
| Outbound ports | A use case, when tested alone | Simple hand-written implementations in memory. No mocking library in the domain or its tests ({AR-PLT-025}).
| Another service of ours | A component test | A simulation generated from that service's contract, so that it cannot answer what the real one would not
| The payment provider | Every level | The simulated provider of the platform, scripted by its tokens ({FR-PAY-007}): the same at every level, up to production in this release
| The e-mail provider | Every level | The simulated provider, which records what it was asked to send
| The database, the bus | A component or integration test | Not replaced: PostgreSQL in a container; the Pub/Sub emulator, or the real service where its schemas matter (document 03-05)
| The clock | Every level below end-to-end | A clock the test moves. Deadlines of minutes are crossed in milliseconds.
|===

.Test data
[%unbreakable, cols="4,11", options="header"]
|===
| Subject | Rule
| Ownership | A test creates what it needs and assumes nothing else exists. No test depends on the data of another.
| Isolation | Each test, or each class of tests, has its own schema, its own topic names, its own customer: tests run in parallel.
| Realism | Built by small builders with sensible defaults: a test states only what matters to it.
| Deployed environments | A script loads a synthetic catalog and accounts (document 06-01). End-to-end tests create their own customer and their own orders on top of it.
| Personal data | Invented. No real person's data appears in a test, a fixture or a recording.
|===

== Quality gates

.Strategy question
****
What strategy turns "well tested" into numbers that block a merge?
****

.Gates on tests
[cols="4,4,7", options="header"]
|===
| Gate | Threshold | Why this number
| Tests pass | All | A failing test is never skipped to merge
| Coverage of the domain | 100 % of lines and of branches ({NFR-MAINT-001}) | The domain is small, pure and where the business lives: no line of it is left to chance. Measured by JaCoCo {v-jacoco}, on the domain packages only.
| Mutation score of the domain | 80 % or more | Coverage says a line ran; mutation says a test would notice if it changed
| State grids | Every cell has a test | Checked by a test that reads the grid and the list of tests
| Acceptance scenarios | Every scenario bound and passing | See above
| Contracts | Every service conforms; no breaking change ({NFR-MAINT-003}) | Document 04-05
| Persistence contract | The suite passes on the three adapters ({NFR-MAINT-004}) | Document 04-04
| Flaky tests | None tolerated | A test that fails without a cause is quarantined the same day, with a ticket, and repaired or deleted within the week
|===

Coverage is not asked of adapters, controllers and configuration as a number.
They are covered by component and integration tests, whose value is in what they exercise, not in a percentage.

== Where each test runs

.Strategy question
****
What strategy places each test in the earliest stage that can run it?
****

[cols="4,7,4", options="header"]
|===
| Stage | Tests | Stops
| Workstation, while writing | Unit tests of the module; component tests of the service being changed | Nothing: the author's own loop
| Pull request | All unit, architecture and mutation tests; all component tests; adapter integration tests in containers; acceptance scenarios bound at component level | The merge (document 06-05)
| After deployment to `test` | Integration tests that need the real services: schemas on Pub/Sub, the persistence contract on the document database, identities and rights; the authorization suite; the dynamic security scan | The release
| After deployment to `integration` | End-to-end tests of the critical paths; the saga scenarios across services; the leak test | The release
| In an announced window | Load tests; the failover drill (document 07-04) | A release that touches performance or the platform
| After deployment to `prod` | Smoke tests | The deployment: automatic return
|===

.In the proof of concept ({ADR-PLT-030})
[%unbreakable, cols="4,11", options="header"]
|===
| Subject | What changes
| Before deployment | Nothing: every test of a pull request runs as above. They need no cloud resource.
| After deployment | The one environment receives the smoke tests, then the end-to-end tests and the saga scenarios that can run on one replica
| Not run | Tests that need a second replica or a standby: the loss of an instance, the failover. Load tests are limited to a short run at the nominal load, to keep the cost within the budget.
| Tests on the real bus and the real document database | Run against the single environment, in topics and collections of their own
|===
