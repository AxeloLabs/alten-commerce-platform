== How the stack is chosen

.Strategy question
****
What strategy produces a stack that is current, coherent as a whole, and still supported when the project ends?
****

A stack is not a list of fashionable tools; it is a set of versions that are known to work together.
Each choice below passed five tests, in this order.

. *Is it imposed?* Spring Boot, Angular, Docker, Kubernetes on GKE Autopilot, Google Cloud Pub/Sub, CloudEvents, Protocol Buffers, Terraform and Secret Manager are constraints of the project. They are not discussed, only versioned.
. *Is it the latest stable release?* Only generally available releases are retained: no milestone, no release candidate, no preview service on a critical path.
. *Is it supported long enough?* A version whose open-source support ends during the project is rejected, even if it is the one everybody knows.
. *Does it fit the others?* The Spring Boot dependency management decides the version of everything it manages. A library is never forced to a version Spring Boot does not manage without a recorded reason.
. *Does it earn its place?* One tool per job. A tool that duplicates what the platform already gives is rejected, and the rejection is written down in <<rejected>>.

Every version in this document was read on the publisher's own release page on {versions-verified-on}.
Versions are declared once, in a single file of the specification, and quoted from there in every document; the same file will feed the build of the code.

== Application framework

.Strategy question
****
What strategy takes everything Spring offers for a service without letting the framework into the business code?
****

Spring is used in the outer layers of each service — web, persistence, messaging, configuration — and is absent from the domain, which is plain Java.
That separation is specified in document 04-03 and enforced by architecture tests.

[cols="4,3,7,7", options="header"]
|===
| Tool | Version | What it does for us | Why this one
| Spring Boot | {v-spring-boot} | Assembles each service: embedded server, configuration, dependency management, health endpoints, container-friendly startup and shutdown. | Imposed. Version chosen for its support window.
| Spring Framework | {v-spring-framework} | Web layer, dependency injection, HTTP service clients, built-in retry and concurrency limits, null-safety annotations. | Brought by Spring Boot.
| HTTP service clients | Spring Framework | Synchronous calls between services, declared as Java interfaces. | Replaces OpenFeign, which is feature-complete and whose own documentation points to this successor.
| Spring Data JPA, Hibernate | {v-hibernate} | The PostgreSQL adapters: mapping, queries, optimistic locking. | The standard pairing with Spring Boot. Confined to adapters; domain objects are never JPA entities.
| Spring Security | {v-spring-security} | Validates the identity token on every request, enforces roles, protects administration functions. | Brought by Spring Boot; native OAuth 2.0 resource-server support.
| Spring Boot Actuator | Spring Boot | Liveness, readiness and startup probes for Kubernetes; metrics and build information. | Built in.
| Spring Modulith | {v-spring-modulith} | Verifies module boundaries inside the two services that hold more than one module (order, cart) and documents them. | Used for its verification and documentation only. Its event registry is not our outbox: it has no Pub/Sub publisher.
| Spring Cloud GCP | {v-spring-cloud-gcp} | Spring integration with Pub/Sub, Secret Manager and Cloud SQL. | The supported bridge between Spring Boot 4 and Google Cloud.
| Spring Cloud | {v-spring-cloud} | Gateway (Server Web MVC), for the web gateway at the edge ({ADR-PLT-018}). | The release train matching Spring Boot 4.1.
| BootUI | {v-bootui} | A developer console inside the running service: beans, configuration, endpoints, requests. | Requested for the project; Spring Boot 4 only. *Development profiles only*: it bypasses the application's security chain, so it is never packaged for a deployed environment.
|===

== Persistence and data

.Strategy question
****
What strategy lets the storage technology change without the business code noticing?
****

The domain talks to storage through ports.
PostgreSQL is the reference for every service that takes part in the order saga; the catalog and the cart additionally prove the ports with a document database and a file.
The design is specified in document 04-04.

[cols="4,3,7,7", options="header"]
|===
| Tool | Version | What it does for us | Why this one
| PostgreSQL | {v-postgresql} | System of record. One database per service, on one managed instance. | Transactions are what make the outbox pattern safe. Managed by Cloud SQL: backups, point-in-time recovery, high availability.
| Flyway | {v-flyway} | Versions the database schema: numbered SQL scripts applied at deployment. | Plain SQL, integrated with Spring Boot. Liquibase moved to a source-available license in its 5.0 release.
| Firestore | Managed service | Document database adapter for the catalog and the cart. | The NoSQL store of Google Cloud. Used through the Google client library: the Spring Data module for Firestore is reactive only.
| JSON file | – | File adapter for the catalog and the cart, for demonstrations and local runs. | Proves that a port can be implemented with no database at all. Never used in a deployed environment.
| H2 | {v-h2} | In-memory database for fast tests of the JPA mappings. | Required for speed. It is not PostgreSQL: anything that relies on row locking or JSON columns is tested on the real database.
| MapStruct | {v-mapstruct} | Generates the mapping code between domain objects, persistence entities and API payloads. | Compile-time generation: no reflection, errors at build time.
| Lombok | {v-lombok} | Removes boilerplate in adapters. | Tolerated outside the domain only; the domain uses records and plain classes.
|===

== API and contracts

.Strategy question
****
What strategy guarantees that two services, or the storefront and a service, never disagree on an interface?
****

Contracts are written first and are the source of truth; code is generated from them or tested against them, never the reverse.

[cols="4,3,7,7", options="header"]
|===
| Tool | Version | What it does for us | Why this one

| OpenAPI Generator | {v-openapi-generator} | Generates the server interfaces of the services and the typed client of the storefront from the contract. | One contract, two generated sides: they cannot drift.
| springdoc-openapi | {v-springdoc} | Serves the contract and an interactive console in non-production environments. | The 3.x line is the one for Spring Boot 4.
| Problem Details | RFC 9457 | The single format of every error response. | Standard, supported natively by Spring.
| Spectral | {v-spectral} | Lints the contracts against the API guidelines. | Rules as code, run in the pipeline.
| oasdiff | {v-oasdiff} | Detects a breaking change between two versions of a REST contract. | Fails the pipeline before the change is merged.
| Microcks | {v-microcks} | Checks that a service honors its REST and asynchronous contracts, and simulates its neighbors in component tests. | Handles OpenAPI and AsyncAPI over Pub/Sub with one tool.

== Resilience

.Strategy question
****
What strategy stops one slow dependency from taking the whole platform down?
****

Resilience patterns guard *synchronous* calls: storefront to services, order to catalog, payment to its provider, notification to the e-mail provider.
Asynchronous exchanges are protected by the bus itself.
The complete strategy is in document 05-02.

[cols="4,3,7,7", options="header"]
|===
| Tool | Version | What it does for us | Why this one
| Resilience4j | {v-resilience4j} | Circuit breaker, bulkhead, time limiter and retry around synchronous calls. | Has a dedicated Spring Boot 4 module. Spring Framework's own resilience features cover retry and concurrency limits only.
| Spring Framework resilience | Spring Framework | Simple retries and concurrency limits by annotation. | Built in; used where a circuit breaker is not needed.
| Pub/Sub retry and dead-letter topics | Managed service | Redelivers a failed message with backoff, then sets it aside after a number of attempts. | The bus already does it; consumers are not wrapped in additional retries.
| Kubernetes | {v-kubernetes} | Restarts failed instances, removes unready ones from traffic, keeps a minimum number running during maintenance. | Built into the platform.
|===

== What was considered and not retained

.Strategy question
****
What strategy prevents the same technology debate from being reopened every month?
****

A rejection is a decision.
It is written here with its reason, and the most structural ones are detailed as architecture decision records in document 04-07.

[cols="4,3,10", options="header"]
|===
| Candidate | Verdict | Reason
| Spring Cloud OpenFeign | Replaced | Feature-complete, maintenance only. Spring HTTP service clients do the same job in the framework itself.
| TestRestTemplate | Replaced | Still available, in a separate module. RestTestClient is the documented default.
| Zipkin | Replaced | Spring Boot is retiring its exporter. OpenTelemetry protocol to Cloud Trace, and to otel-lgtm locally.
| Loki, loki4j appender | Not needed | GKE collects standard output into Cloud Logging. Loki is present only inside the local otel-lgtm container.
| Liquibase | Replaced | License changed to a source-available one in 5.0. Flyway covers the need with plain SQL.
| Jenkins | Rejected | A server to host, patch and secure. GitHub Actions is managed.
| Cloud Deploy | Rejected | Driven by a Skaffold configuration, and its progressive delivery needs a route per workload ({ADR-PLT-031}).
| Two-phase commit | Rejected | No transaction manager spans PostgreSQL, Pub/Sub and several services, and a coordinator would couple their availability. Saga and outbox instead; explained in document 04-06.
| gRPC | Deferred | A second contract technology for very few synchronous calls. Spring gRPC is generally available: the door stays open.
| Apache Flink | Rejected | A stream-processing engine; the platform has no stream analytics.
| State machine engine, workflow engine | Rejected | Excluded by the brief. Order and saga states are plain domain code, fully unit-tested.
| Spring Cloud Kubernetes, Config Server, Eureka | Not needed | Kubernetes already provides discovery, load balancing and configuration.
| Spring Cloud Stream binder for Pub/Sub | Not needed | An abstraction over a bus we will not replace. The Pub/Sub template and subscriber are used directly, inside adapters.
| Springwolf | Not usable | Generates AsyncAPI from code for Kafka, AMQP and others; it cannot scan Pub/Sub listeners.
| Spring Modulith event registry | Not used | A persistent event log without a Pub/Sub publisher. The transactional outbox is implemented explicitly, behind a port.
| Chaos Mesh | Not usable | Needs privileges that Autopilot does not grant. Faults are injected by the simulated provider and by stopping pods.
| Skaffold | Rejected | Announced for archival in January 2027.
| Trivy | Replaced | Works, but its release pipeline was compromised in March 2026. Grype and Syft are retained; whatever is used is pinned by digest.
| k6 | Alternative | Equally capable. Gatling is preferred for scenarios in Java and its license.
| Gradle | Alternative | Equally capable. Maven is preferred for its ubiquity in enterprise Java teams.
| Jira | Not retained | The backlog lives in GitHub Issues and Projects ({ADR-PLT-032}). Should an employer impose Jira, the backlog would be structured the same way.
| Cloud Build | Not retained | Google's build service would do the work of GitHub Actions, away from the repository, its reviews and its backlog. A second home for pipeline definitions adds nothing at this size.
| nginx | Not needed | The web gateway serves the files of the storefront: one workload less (document 04-03).
| Mermaid | Not retained | Renders in many viewers without a tool, and suits simple flows. PlantUML is kept because one syntax covers UML, C4, state, sequence and network diagrams with addresses, with a shared style and a build that needs no network ({ADR-PLT-029}).
| Graphviz, written by hand | Used underneath | PlantUML lays out most of its diagrams with it. Writing its language directly gives boxes and arrows, without the notations of UML or C4.
| Micro front ends | Not retained | The storefront is one Angular application, built and released as a whole: one team, one design, one release. Splitting it would add a composition layer and several pipelines, for no independent team to benefit.
| GKE and gcloud MCP servers for the AI agent | Not needed | They add nothing the `gcloud` and `kubectl` command lines do not already do, and they widen what an agent can change. See documents 08-01 and 08-02.
|===

== Points to watch

.Strategy question
****
What strategy tells us today where the stack could bite tomorrow?
****

[cols="5,10", options="header"]
|===
| Point | What we do about it
| Spring Boot 4.2 will be released during the project | Stay on 4.1 until 4.2 is released and Spring Cloud GCP supports it; then upgrade through a dedicated change.
| Jackson 3 is the default in Spring Boot 4 | New package names. Any library still tied to Jackson 2 is checked before it is added.
| PIT with JUnit {v-junit} | The JUnit plugin of PIT has not been released since 2025. Prototype it before mutation testing becomes a gate; otherwise keep it as a report.
| The Pub/Sub emulator does not validate Protobuf schemas | Schema compatibility is checked by buf in the pipeline and by tests against the real Pub/Sub of the test environment.

== Version policy

.Strategy question
****
What strategy keeps the stack current without a migration project every year?
****

* Versions are declared in one place and nowhere else.
* Everything Spring Boot manages follows Spring Boot; a patch release of Spring Boot is adopted within two weeks.
* Dependency updates arrive as pull requests from Renovate and go through the same gates as any change.
* A minor or major upgrade of the baseline (Java, Spring Boot, Angular, Kubernetes) is a planned change with its own decision record.
* Images, pipeline actions and scanners are pinned by digest.
* This document is re-verified at each baseline upgrade, and its verification date updated.
