== Principles

.Strategy question
****
What strategy lets a change reach production the same day, without anyone having to trust that it is safe?
****

One tool does the whole path ({ADR-PLT-031}).
GitHub Actions builds, tests, scans and publishes images, then deploys them, environment after environment, by applying the Helm charts of document 06-03.
Nothing else stands between a commit and a running pod: no pipeline server to host, no second delivery product.

.Six rules
[cols="4,11", options="header"]
|===
| Rule | Meaning
| Built once | An image is built by one run and deployed unchanged everywhere. What reaches production is, bit for bit, what was tested (document 06-01).
| Gates, not opinions | Every check has a threshold and blocks. Nothing is "to be looked at later".
| Security is in the line | Secrets, dependencies, images, infrastructure and the running application are checked by the same pipeline as the tests, not by a separate audit.
| Fast first | Checks run from the quickest to the slowest: an author learns of a formatting error in a minute, not after the load test.
| Only what changed | A change to one service builds and deploys that service. The contracts and the shared starter rebuild what depends on them.
| One human gate | A person reviews each pull request, and a person approves each production deployment. Everything else is automatic.
|===

.Branches and versions
[%unbreakable, cols="4,11", options="header"]
|===
| Subject | Rule
| Main branch | Always deployable. Protected: no direct push, no merge without the gates and a review.
| Work | Short-lived branches, one pull request per change, merged within days.
| Release | Each merge that changes a deployable part creates a release: a version made of the date and a sequence number, tied to the commit, with the digests of its images and the versions of its charts.
| Pipeline definitions | YAML files of the repository, reviewed like code; their owners are named, and a change to them needs their approval.
|===

== The pipeline of a pull request

.Strategy question
****
What strategy tells an author everything that is wrong with a change before anyone else spends time on it?
****

plantuml::diagrams/pipeline-pr.puml[format=svg, align=center, pdfwidth=80%]

.Stages and their gates
[cols="3,6,4,5", options="header"]
|===
| Stage | What runs | Tools | Blocks when
| Secrets | Scan of the commits | gitleaks {v-gitleaks} | Anything that looks like a secret ({NFR-SEC-004})
| Contracts | Style; compatibility with the main branch | Spectral {v-spectral}, oasdiff {v-oasdiff}, buf {v-buf}, AsyncAPI CLI {v-asyncapi-cli} | A rule of documents 03-04 or 04-05 is broken; a change breaks a consumer ({NFR-MAINT-003})
| Build | Formatting, compilation with static checks, unit tests | Maven {v-maven}, Spotless {v-spotless}, Error Prone {v-error-prone}, NullAway {v-nullaway}, JUnit {v-junit} | A file is not formatted; a warning; a failing test ({NFR-MAINT-005})
| Architecture | The rules of document 04-03 | ArchUnit {v-archunit}, Checkstyle {v-checkstyle} | One violation ({NFR-MAINT-002})
| Domain | Coverage, then mutation testing, of the domain packages | JaCoCo {v-jacoco}, PIT {v-pitest} | Coverage below 100 % of lines and branches; mutation score below its threshold ({NFR-MAINT-001})
| Components | Each service with its real adapters, in containers | Testcontainers {v-testcontainers}, Microcks {v-microcks} | A failing test; a service that does not conform to its contract
| Storefront | Lint, unit tests, build | Angular {v-angular} tooling | An error
| Code analysis | Defects, duplications and security rules on the code that changed | SonarQube, hosted edition | The quality gate on new code fails
| Dependencies | Inventory of components, known vulnerabilities | Syft {v-syft}, Grype {v-grype} | A critical or high vulnerability with a fix available ({NFR-SEC-005})
| Infrastructure | Validation and security scan of Terraform and of the rendered charts; plan posted | Terraform {v-terraform}, Checkov {v-checkov}, Helm {v-helm} | A resource exposed, unencrypted or over-privileged; a chart that does not render
| Documentation | Build of this specification, when it changes | The documentation toolchain | A broken identifier or reference
|===

A pull request is answered within a quarter of an hour.
Stages that do not depend on each other run in parallel, and a stage runs only if something it concerns has changed.

The code analysis uses the hosted edition of the product: a server of our own would cost more to run than the whole proof of concept ({ADR-PLT-030}).
Where that service is not configured, the stage is skipped and says so; the other gates do not depend on it.

.Rules for exceptions
[%unbreakable, cols="4,11", options="header"]
|===
| Subject | Rule
| A vulnerability with no fix available | Recorded with a reason and an expiry date, in a file of the repository that is itself reviewed. It blocks again when the date passes.
| A false positive of an analysis | Marked where it occurs, with a reason. Never by lowering a threshold.
| Skipping a gate | Not possible from a pull request. The protection of the main branch belongs to the owners of the repository.
|===

== The pipeline of the main branch

.Strategy question
****
What strategy moves a merged change to production with evidence at each step and a way back at the last?
****

plantuml::diagrams/pipeline-release.puml[format=svg, align=center, pdfwidth=72%]

.Steps
[cols="3,7,5", options="header"]
|===
| Step | What happens | Stops when
| Images | Built for the parts that changed; inventoried; scanned; signed; attested for admission; pushed. Images of products we do not build — the identity provider, the trace collector, Grafana — are copied into our registry and go through the same scan and attestation: no pod pulls an image from elsewhere. | A critical or high vulnerability in an image; a signature or an attestation that cannot be made
| Release | Recorded in the repository: its version, the digests of its images, the versions of its charts | –
| Deployment to `test` | One job, bound to the environment `test`. It applies the infrastructure of the environment if it changed, then each chart that changed. | A migration fails; a pod does not become ready
| Tests of `test` | The tests that need real services, the authorization suite, the dynamic scan with ZAP {v-zap} | A failing test; a finding of high severity ({NFR-SEC-008})
| Deployment to `integration`, and its tests | The same release, the same way. End-to-end tests of the critical paths with Playwright {v-playwright}; saga scenarios with failures provoked | A failing test
| Approval | The job bound to the environment `prod` waits until a person named for that environment approves, with the evidence of the previous steps in front of them | Not approved
| Deployment to `prod` | The same release, the same way, then a verification of the critical paths | A pod not ready, or a failed verification: automatic return to the previous release
|===

.How a chart is applied
[cols="4,11", options="header"]
|===
| Step | Mechanism
| Migrations | A job declared in the chart as a step that Helm runs before it changes anything else. If it fails, nothing of the release is applied (document 04-04).
| Replacement | The rolling update of document 06-03: one new pod at a time, ready before an old one stops.
| Waiting | Helm waits until every new pod is ready, within a time limit.
| Failure | Helm returns by itself to the revision that was in place. The job fails, and the pipeline reports it.
| Record | The revision history of Helm in the cluster, and the deployment history of the environment in GitHub, say what runs where and since when.
|===

There is no share-of-traffic step.
Only the web gateway and the identity provider receive traffic through a route; the six services are reached by name inside the cluster or by messages, where a share of traffic has no meaning.
What limits the harm of a faulty version is therefore the same for every workload: one pod at a time, readiness, the verification, and the automatic return.

Load tests and platform drills are not part of every release.
They run on `integration` in an announced window, before a release that touches performance or the platform (document 07-04): the three environments share one database instance, and a load test at any hour would be a load on production.

.Return and urgency
[%unbreakable, cols="4,11", options="header"]
|===
| Subject | Rule
| Rollback | Deploying the previous release again, by the same pipeline. Always possible: migrations never break the previous version (document 04-04).
| Urgent fix | The same path. The gates are what make a fast fix safe; none is skipped.
| A failed release | Never repaired in place. The fix is a new commit and a new release.
|===

.The proof-of-concept profile
[%unbreakable, cols="4,11", options="header"]
|===
| Subject | What changes ({ADR-PLT-030})
| Environments | One. The pipeline of the main branch stops after recording the release.
| Deployment | Started by the owner, who gives the deadline of destruction at the same time (document 06-06). The same job, the same charts, with the values of the profile.
| Tests after deployment | The verification of the critical paths. The suites of `test` and `integration` run against the same single environment, on request.
| Destruction | A scheduled run of the pipeline destroys everything at the deadline (document 06-04).
|===

== Security gates

.Strategy question
****
What strategy shows on one page every security check a change must pass?
****

The brief asks which security gates the pipeline has.
They are spread over the two pipelines above; this table gathers them.

.Security gates, in the order a change meets them
[cols="1,4,3,4,5", options="header"]
|===
| # | Gate | Where | Tool | Blocks
| 1 | No secret in the code | Pull request | gitleaks | Any finding
| 2 | No unsafe pattern in the code | Pull request | SonarQube | New security issues
| 3 | No known vulnerability in dependencies | Pull request | Syft, Grype | Critical and high
| 4 | No unsafe infrastructure | Pull request | Checkov | Public, unencrypted or over-privileged resources
| 5 | Deployments ask for no privilege | Pull request | Chart validation against the restricted profile | A pod that asks for more
| 6 | No known vulnerability in images | Main branch | Grype | Critical and high
| 7 | Images come from us | Main branch, then the cluster | cosign {v-cosign} for the signature; Binary Authorization for admission | See below
| 8 | Authorization holds | `test` | The authorization suite | Any cell of the matrix that fails ({NFR-SEC-002})
| 9 | The running application resists common attacks | `test` | ZAP | A finding of high severity
| 10 | Nothing sensitive in logs | `integration` | The leak test after the end-to-end tests | Any personal data, token or secret ({NFR-SEC-007})
| 11 | A person agrees | Before `prod` | The protection of the environment `prod` | No approval
|===

.Gate 7 in detail
[%unbreakable, cols="4,11", options="header"]
|===
| Step | What happens
| Signature | The pipeline signs each image with cosign, without a stored key, using the identity of the run. The signature travels with the image and can be verified by anyone.
| Attestation | Once the scans have passed, the pipeline records an attestation of the image with a key held in the key management service of the project. Only the identity of the main-branch pipeline may use that key.
| Admission | The cluster runs Binary Authorization in blocking mode: a pod whose image has no attestation from our attestor is refused, whoever asks.
| Scope | Every namespace of ours. System workloads of the platform are exempted by the platform itself.
|===

== How the pipeline authenticates

.Strategy question
****
What strategy gives a pipeline the power to deploy without leaving a key that could be stolen?
****

[cols="4,11", options="header"]
|===
| Subject | Rule
| To Google Cloud | GitHub proves which repository, which branch and which environment a job belongs to; Google Cloud exchanges that proof for a credential that lives minutes. No key is stored anywhere.
| One identity per purpose | A job of a pull request can read, build and compute a plan. A job of the main branch can push images. A job bound to an environment receives the deployment identity of that environment, and of no other.
| Production | The deployment identity of `prod` is issued only to a job of the main branch, bound to the environment `prod`, after the approval. A run cannot obtain it by naming the environment: the approval is enforced by GitHub before the job starts.
| Third-party steps | Pinned to an exact commit, and few. Each job declares the minimum rights it needs.
| Code from outside | A pull request from a fork runs without any credential and without any secret.
| The pipeline's own secrets | The token of the code analysis, and nothing else. Readable by runs of branches of the repository, never by runs of forks.
|===

== Measuring delivery

.Strategy question
****
What strategy tells whether the pipeline is helping or merely passing?
****

[%unbreakable, cols="5,5,5", options="header"]
|===
| Measure | Target | Read on
| Time from a merge to production | Within a working day | The deployment history
| Deployments to production | Several per week | The deployment history
| Share of releases that are rolled back | Below 15 % | The deployment history
| Time to restore after a failed release | Below 30 minutes | Alerts and deployment history
| Answer to a pull request | Below 15 minutes | Pipeline durations
| A gate that fails for no good reason | Rare, and fixed first | Count of re-runs
|===

A gate that is often re-run until it passes is a broken gate: it is repaired or removed, never ignored.
