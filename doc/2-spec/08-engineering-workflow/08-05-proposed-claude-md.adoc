== What the file is for

.Strategy question
****
What strategy tells every agent, at the start of every session, the few things it must never get wrong?
****

An agent that opens this repository knows nothing of the project.
`CLAUDE.md`, at the root, is read into its context at the start of each session: it is the page that a newcomer would be given on the first morning.

It is written for a reader with no memory and little room.
Every line is read at every session and competes with the task for attention: the file says only what applies everywhere, and points to the rest.

.Five places for instructions, and what each is for
[cols="4,6,5", options="header"]
|===
| Place | Holds | Read
| `CLAUDE.md` | What is true everywhere in the repository: where the truth is, the layout, the commands, the rules that are never suspended | At every session
| Rules by folder | What is true in one part of the code: the domain, messaging, the storefront, the infrastructure | When the agent works in that part
| A creation prompt (document 08-03) | One increment: what to build, what to read, which tests prove it | For that task
| The specification | Everything else, in full | When a prompt or the file names a document
| The settings of the harness (document 08-02) | What is refused, whatever the agent was told | By the harness, not by the agent
|===

The last line is the important one.
An instruction file is context; it enforces nothing.
Whatever must hold even against a mistaken or deceived agent is enforced elsewhere, and the table of the third section says where.

.How it is written
[%unbreakable, cols="3,12", options="header"]
|===
| Rule | Meaning
| Short | Eighty lines. The documentation of the tool advises to stay under two hundred per file; attention is better spent on the task.
| Specific | "Never publish to Pub/Sub directly: write to the outbox", not "follow good practices". A rule that cannot be checked is removed.
| A pointer, not a copy | The file names the document that holds a subject; it does not repeat it. The specification changes in one place.
| Nothing secret, nothing personal | The file is committed. Personal preferences go in a local file that is not.
| Reviewed | It is an instruction to every future agent: a change to it is reviewed by its owners, like a change to the pipeline (document 08-02)
|===

== The text

.Strategy question
****
What strategy gives the exact words, so that nothing is left to be reinvented at the first session?
****

The text below was shown to the product owner and validated on 2026-11-19.
It was written at the root of the repository the same day, ahead of the code: the commands it names exist from the first increment on ({CRE-PLT-001}), which confirms each of them by running it and corrects the file if one differs.

.`CLAUDE.md`
[source,markdown]
----
# alten-commerce-platform

An e-commerce order platform: six Spring Boot services, an Angular storefront behind a
web gateway, Google Pub/Sub, PostgreSQL, on GKE Autopilot.

[Specification](#the-specification-decides) · [Layout](#layout) · [Commands](#commands) ·
[Code](#code) · [Tests](#tests) · [Work](#work) · [Never](#never)

## The specification decides

- `doc/2-spec/` is the source of truth. Read the documents your task names before you write.
  New here? Start with `doc/2-spec/00-overview/00-02-architecture-big-picture.adoc`.
- Never change the specification to fit the code. Where it is ambiguous, incomplete or seems
  wrong: take the most conservative reading and report the point with its identifier.
- Build nothing the specification does not ask for.
- Everything has an identifier (`UC-ORD-001`, `FR-INV-003`, `TU-ORD-005`, `ERR-ORD-002`).
  Keep it in the code: tag each test with its identifier, name an architecture test after
  its `AR` rule, return the `ERR` code of the catalog.

## Layout

| Path | Content |
|---|---|
| `contracts/` | OpenAPI, AsyncAPI, Protobuf. Written first, by hand. |
| `platform-starter/` | Shared technical library. No business type. |
| `services/<name>/` | catalog, inventory, cart, order, payment, notification |
| `web/` | `storefront` (Angular) and `web-gateway` |
| `acceptance/` | Acceptance scenarios, bound to the application code of all services |
| `deploy/` | `terraform/` and `helm/` |
| `doc/` | The specification |

## Commands

| Need | Command |
|---|---|
| Install the toolchain | `mise install` |
| Build and check everything | `./mvnw verify` |
| One service and what it needs | `./mvnw -pl services/order-service -am verify` |
| Format (never by hand) | `./mvnw spotless:apply` |
| Storefront tests | `pnpm --dir web/storefront test` |
| Local platform | `podman compose up -d` |
| Check the specification | `doc/2-spec/build.sh --check` |

## Code

- Three rings in a service: `domain` depends on nothing, `application` on `domain`,
  `adapter` on both. No framework, no persistence or JSON annotation in `domain`.
- A business refusal is a result of the domain, not an exception.
- A change of state and the messages it causes are saved in one unit of work.
  Never publish to Pub/Sub directly: write to the outbox.
- Every message handler is idempotent: the same message twice has its effect once.
- Time and identifiers are given to the domain, never read by it.
- Value objects are records, valid by construction. `Money`, never a bare number.
- No Lombok in `domain` or `application`.
- English everywhere: code, comments, logs, commit messages.

## Tests

- Tests first, from the specification: one test per rule, per cell of a grid.
- `domain` is covered at 100 % of lines and branches. No mocking library in its tests.
- Never make a test pass by weakening it, deleting it or lowering a threshold.
- No `sleep`, no real clock, no data shared between tests.

## Work

- One increment at a time: a creation prompt (`CRE-…`, document `08-03`), on its own
  branch, as one pull request.
- Stay in the scope the prompt gives. Do not touch `contracts/`, `platform-starter/`,
  pipeline definitions or quality thresholds unless the increment is about them.
- No dependency outside document `04-01`, unless you report it with its reason.
- End with the report the prompt asks for: what was built, each test identifier and its
  state, what was not done, every assumption.

## Never

- Deploy, apply infrastructure, or change anything in a cluster or in Google Cloud.
  The pipeline does that.
- Push to `main`, force a push, skip the checks of a commit.
- Read credentials, or put a secret or a real person's data anywhere.
- Work around a refused command. The refusals are those of documents `06-06` and `08-02`.
----

== Why each part is there

.Strategy question
****
What strategy keeps a rule of the file from being only a hope?
****

Each part of the file states a rule of the specification in one line.
None of them relies on the file to be respected: the right column says what stops a change that ignores it.

[cols="4,6,5", options="header"]
|===
| Part | Why it is in the file | What really enforces it
| The specification decides | An agent left alone fills gaps with plausible inventions. It must know where the truth is, and that a gap is to be reported. | The specification reviewer of document 08-03; the report every prompt asks for
| Identifiers kept in the code | Traceability ends where an identifier is dropped | A catalogued test that is missing fails the build; an expert checks the tags
| Layout | Saves the exploration of every session, and says where nothing may be shared | The architecture rules (document 04-03)
| Commands | An agent that guesses a command guesses wrong half the time | –: they are information
| Three rings; no framework in the domain | The most frequent slip of generated code | Architecture rules {AR-PLT-001} and following, at every build
| Unit of work, outbox, idempotent handlers | The promises of the saga rest on them | Architecture rules; the tests of document 07-02; the transaction reviewer
| Records, `Money`, no Lombok in the domain | Conventions of document 04-03 | Architecture rules and static checks
| English everywhere | The brief | Review
| Tests first; 100 % of the domain | Tests written after the code prove the code, not the rule | The coverage and mutation gates; the test reviewer
| Never weaken a test or a threshold | The shortest way to a green build | The thresholds have owners; reviewers read the tests first
| One increment, one scope | A change that touches everything cannot be reviewed | The scope of the prompt; the review
| Never deploy, never touch the cloud | The one kind of mistake that cannot be taken back | The agent holds no identity that can (document 08-02)
| Never read credentials | – | The session account holds none; the sandbox and the read refusals
| Never work around a refusal | An agent that meets a refusal tends to look for another way | The refusal is repeated by layers the agent cannot reach
|===

== Rules by folder

.Strategy question
****
What strategy gives detailed rules where they apply, without making every session read all of them?
****

The tool loads a rule file only when the agent works on files that match the paths the file declares.
What concerns one part of the code is written there, and costs nothing elsewhere.

.Rule files of the repository
[cols="3,5,8", options="header"]
|===
| File | Applies to | Says
| `domain` | The domain packages of every service | Plain Java; no annotation of a framework; aggregates changed through their root; refusals as results; value objects as records; no clock, no random identifier
| `messaging` | The messaging adapters; the contracts of messages | Envelope and its attributes; acknowledgement rules; the inbox first; nothing published outside the outbox; a schema never loses a field
| `persistence` | The persistence adapters; migrations | Migrations only add, and are never edited once merged; entities are not domain objects; rows written in SKU order
| `rest` | The REST adapters; the OpenAPI documents | The contract first; error answers from the catalog; paging and its maximum; deny by default
| `storefront` | The Angular application | Clients generated from the contracts; no token in the browser; a message per error code; accessibility
| `deploy` | Infrastructure code and charts | The two profiles differ by values only; every resource labeled; nothing that document 06-06 forbids or did not count
| `specification` | The documents of this specification | The conventions of document 00-01: identifiers, role tags, a strategy question at the top of each section, versions quoted from the shared file
|===

.The shape of a rule file
[source,markdown]
----
---
paths:
  - "services/*/src/main/java/**/domain/**"
  - "services/*/src/test/java/**/domain/**"
---

# Domain code

- Plain Java. No import from Spring, from the persistence library or from Jackson.
- An aggregate is changed only through its root, and is valid after every method.
- A business refusal is returned as a result. Exceptions are for what should not happen.
- No clock and no random identifier: both are parameters.
----

The rule files are written with the harness ({CRE-PLT-002}).

The brief wondered whether its habit of opening every section with a "strategy" question belonged in this file.
It does not: it is a convention of the documents, useless to an agent that writes Java.
It lives in the rule file of the specification, and is read only by an agent that edits a document.

== Keeping it true

.Strategy question
****
What strategy prevents the file from becoming a list of old advice that nobody dares to delete?
****

[%unbreakable, cols="4,11", options="header"]
|===
| Subject | Rule
| When a command changes | The file changes in the same pull request
| When an agent makes a mistake that the file should have prevented | First ask whether a mechanism can prevent it: a test, an architecture rule, a refusal of the harness. A line is added to the file only when none can.
| When a line is no longer true | It is deleted. The file never grows without something leaving it.
| What does not belong | A rule that a tool already enforces without help; explanations; history; anything personal
| Personal preferences | A local file next to it, not committed, and the developer's own file outside the repository
| Review | Every change, by the owners of the file
|===
